## Progressive real-music delivery experiment

Recorded 24 October 2026 MYT (23 October UTC), following PR #8. The new opt-in live server uses the same tested Music-client SABR/token combination, but returns received audio bytes over same-origin HTTP before complete retrieval. Selecting **Use live music** reads only the fixed catalog metadata; Play starts the selected song's upstream retrieval. Metadata labels come from the existing prepared manifest; the live route never reads its audio files or substitutes tones/prepared bytes on failure. The default `npm start` server continues without a browser or token service; `npm run start:live` explicitly opts into those development dependencies at runtime.

The server retains at most three fixed captures, each capped at 16 MiB, until process restart. Requests for the same song share its growing buffer, including byte-range requests for seeking. A request for an unavailable later byte waits for the source; this is not upstream time-based random access. Each capture has a 90-second deadline and fetches have 15-second deadlines. Completion requires EOF, exact advertised length and no recorded source error. The final response byte is withheld until verification. Earlier audio is necessarily usable before whole-file integrity is known. Failed captures remain failed for that process run; there are no retries, arbitrary URLs, eviction, session/token renewal or next-track prefetch. Browser disconnection does not cancel the shared bounded capture, allowing a subsequent seek/reconnection to reuse it.
