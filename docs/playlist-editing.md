# Editing owned playlists

My library → **Load my playlists with Google** → Open playlist → **Edit playlist**. Move songs up/down, remove an occurrence, or use **Find songs** and **Add to draft**. **Save to YouTube** sends the draft; **Discard draft** leaves YouTube unchanged. Playback and its queue stay independent of this draft.

The owner confirmed that playing, seeking and skipping from the Google-connected view worked before this change. The editor's automated proof uses synthetic playlists and simulated Google responses; no real playlist edits were made during implementation.

## Permission and bounds

Existing broader Google authorization can be reused. A read-only grant can still browse and play; **Allow playlist saving → Enable Google playlist editing** explicitly requests `https://www.googleapis.com/auth/youtube` (Google: Manage your YouTube account). Connecting leaves the page and stops playback. No permission is widened automatically, and no cookie/header refresh is involved. The optional direct-Music OAuth diagnostic remains separate.

Editing is available for ordinary PL playlists in the first 50 owned playlists returned by Google. The entire playlist must fit within 100 tracks, with valid video and occurrence IDs. Truncated playlists, unavailable entries and Music-only collections remain playable where possible but cannot be edited here. There is no per-save ten-change cap. The original and desired playlists bound the plan to at most 200 writes for the existing 100-song editor. Google quotas and upstream failures still apply. Removing an entry does not rewrite the positions of every later song.

The existing anonymous Music search supplies at most 30 song results. Search terms, private playlist contents and editing tickets are not added to the exported device log. Drafts are in page memory only; leaving/reloading an unsaved draft asks before discarding it.

## What a save does

The owner-only HTTPS `POST /api/account/oauth/save` accepts at most 32 KiB JSON with playlist ID, single-use editing ticket and ordered occurrence/video IDs. The server validates the whole draft before writing. It reads the playlist again and compares occurrence identities and order with the original snapshot, rejecting an already changed playlist without writes. Duplicate videos remain distinguishable by their playlist-item IDs.

A ticket expires after ten minutes, is replaced when another Google playlist is opened, and disappears on restart. It is consumed before the save preflight. One OAuth action runs at a time; a consumed ticket cannot replay, including after a timeout, disconnect or restart. Validation errors before consumption allow correcting the draft. Other save failures require reloading and inspection before another edit. Google errors and bodies are not exposed.

Only the official [playlistItems.insert](https://developers.google.com/youtube/v3/docs/playlistItems/insert), [update](https://developers.google.com/youtube/v3/docs/playlistItems/update) and [delete](https://developers.google.com/youtube/v3/docs/playlistItems/delete) endpoints are used. Removed occurrences are deleted first, followed by required inserts/moves. Each request has a ten-second deadline, no redirects and no automatic retry. The POST validates and starts one in-memory save, returning202 with its random save ID. The owner-only parameter-free GET /api/account/oauth/save-status returns only that ID, state/phase, acknowledged and total counts, and fixed error text. It bypasses the OAuth action lock so status can be read while saving. Writes run sequentially with one action lock held through final readback. Tokens renew between operations if needed. Successful Save requires the final video order and surviving occurrence IDs to match the draft.

**Saving is not atomic.** A failure may leave some requested changes on YouTube, including removals. There is no automatic rollback. An external edit made during the multi-request save can also race; the final readback can report a mismatch but cannot prevent every concurrent edit. Avoid editing the same playlist in another client while saving. Reverting Coda's code does not undo saved playlist changes or restore removed occurrence identities. Playlist title/visibility and the old consumed one-time test journal are untouched.

## Larger saves and recovery

The owner reported “tested seems fine” for the first editor. Exact tested operations and official-site readback were not supplied, so this remains an owner observation rather than a fully specified write test.

A Save now starts one server operation and the page polls read-only progress every half second. The UI distinguishes preflight, confirmed changes and final verification. Refreshing the page or checking status after a lost status request monitors that operation; it never resends mutations. Session storage retains only a random save ID (no account/playlist data). If storage is unavailable, an active server save can still be discovered. If server state is lost/replaced, the page reports the outcome unavailable and asks for inspection. A confirmed save result survives a subsequent failure to reload the playlist view.

Only the latest save status is held in memory. A process restart can interrupt it and discard status; it does not resume or replay writes. Closing a tab does not cancel an accepted save. No cancellation, automatic rollback or automatic retry is offered. The visible count represents successful HTTP acknowledgments, not a guarantee about the uncertain last operation. Final success still requires exact readback. A new save cannot overlap a running save; consumed tickets cannot replay.

The larger-save fixture accepts12 inserts, pauses after one acknowledged write, exposes progress through the owner gate, rejects overlap, then verifies all12. A failure on write4 stops with3 acknowledgments and never retries. Browser proof covers progress beside Save, a failed status request and Check save status, refresh recovery, missing server state, preserving a verified result after UI reload failure, and preserving a newer unsaved draft when inspecting an older save. No additional real-account writes were made.
